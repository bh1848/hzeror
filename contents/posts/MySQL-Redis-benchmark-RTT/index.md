## 낮은 Latency와 엇갈리는 제한된 처리량(OPS)

Redis는 단일 인스턴스에서도 초당 10만 회 이상의 연산(OPS)을 처리할 수 있는 고성능 In-Memory DB이다. 하지만 본 프로젝트의 벤치마크 결과, Redis의 응답 속도는 MySQL 대비 압도적으로 빠름에도 불구하고($0.17ms$ vs $1.05ms$), 절대적인 처리량(Throughput) 수치는 수백만 OPS에 도달하지 못했다.

서버의 CPU나 메모리 리소스는 충분한 대기(Idle) 상태를 유지함에도 클라이언트가 더 이상의 부하를 인가하지 못한 것이다. 나는 이 병목(Bottleneck)이 DB 서버 내부가 아닌 **요청자(Client) 구간에 존재하는 상황**으로 생각했다.

## 동기식(Synchronous) 구조와 Stop-and-Wait 프로토콜

이 현상은 벤치마크 클라이언트의 구현 방식인 **Blocking I/O**와 물리적 한계인 **RTT(Round Trip Time)**가 결합된 구조 때문에 발생하는 것이다.

작성된 코드를 분석하면, 각각의 데이터 요청은 이전 명령어의 응답(ACK)을 수신할 때까지 스레드를 완벽히 대기(Block)시킨다.

~~~java
// 요청 -> 대기 -> 응답수신 -> 다음 요청 (Stop-and-Wait)
for (int i = 0; i < BATCH_SIZE; i++) {
    // 동기식 호출이므로 Thread는 네트워크 응답 시까지 유휴 상태로 Block된다.
    redisTemplate.opsForValue().get(key); 
}
~~~

이 구조는 전형적인 **Stop-and-Wait** 프로토콜로 동작하며, 네트워크 선로를 점유하는 시간보다 대기하는 시간이 더 길어지는 비효율을 초래한다.

## 전체 레이턴시 구성 요소와 물리적 하한선

이 구조에서 클라이언트가 체감하는 전체 레이턴시($T_{total}$)는 다음 수식으로 정의된다.

$$T_{total} = T_{proc} + T_{rtt} + T_{serialize}$$

Redis 내부 처리 시간($T_{proc}$)이 $1\mu s$ 수준으로 극한으로 짧더라도, 데이터가 네트워크를 타고 왕복하는 시간($T_{rtt}$)이 $0.1ms$라면, 클라이언트의 최소 응답 시간은 물리적으로 $0.1ms$ 이하로 떨어질 수 없음을 파악했다.

> **[RTT](https://www.google.com/search?q=Round+Trip+Time)**  
> 데이터 패킷이 출발지에서 목적지로 이동하고, 다시 출발지로 돌아오는 데 걸리는 시간을 의미한다. 로컬호스트(Loopback) 환경이라도 OS의 네트워크 스택(TCP/IP Stack)을 거치는 비용이 발생하며, 이는 성능의 물리적 하한선(Lower Bound)으로 작용한다.

## Network Bound 한계와 Client Side Latency 채택 근거

결과적으로 동기식 클라이언트에서의 최대 OPS는 레이턴시의 역수($\frac{1}{Latency}$)로 수렴한다. 평균 레이턴시가 $0.2ms$일 때 이론상 낼 수 있는 최대 OPS는 초당 $5,000$회($\frac{1}{0.0002}$)로 제한된다. 이는 클라이언트가 네트워크 응답을 대기하는 전형적인 **'Network Bound'** 상태를 증명한다.

나는 이 이것을 해결하기 위해 응답을 기다리지 않는 파이프라이닝(Pipelining) 기술 도입을 고려했으나, 의도적으로 동기식 방식을 유지하고 **'Client Side Latency'**를 핵심 지표로 고정하는 트레이드오프로 결정했다.

대부분의 실무 웹 애플리케이션 비즈니스 로직은 DB에서 데이터를 단건 조회 후 그 결과를 바탕으로 다음 로직을 분기하는 순차적(Sequential) 흐름을 띤다. 따라서 비현실적인 최대 처리량 수치보다는, **"애플리케이션이 코드를 실행했을 때 언제 제어권을 돌려받는가"**를 측정하는 것이 실제 서비스 환경의 레이턴시를 대변한다고 판단했다.

이 방시은 순수 연산 속도 측정에는 불리하지만, 네트워크 I/O 비용과 직렬화 비용을 모두 포함하여 MySQL과 Redis의 체감 성능 차이를 가장 공정하게 대조할 수 있다.
