**D-HASH**는 특정 키의 요청량이 임계치를 초과할 경우, 트래픽을 주 노드(Primary)와 대체 노드(Alternate)로 분산시키는 동적 라우팅 전략을 취한다.

하지만 초기 구현 단계에서 간과했던 치명적인 문제가 발견되었다. 바로 **핫키로 승격되는 즉시 트래픽을 분산할 경우, 데이터가 없는 대체 노드로 요청이 전달되어 대량의 캐시 미스가 발생하는 현상**이었다. 이는 DB 부하를 줄이려는 본래 목적에 역행하여 오히려 시스템 전체의 지연 시간을 급증시키는 원인이 되었다.

이 '콜드 스타트(Cold Start)' 문제를 해결하기 위해 도입한 **Guard Phase(예열 구간)**의 설계 의도와 구현 내용을 정리한다.


## 핫키 승격 직후의 데이터 부재와 콜드 스타트 병목 현상

### 현상 분석: 준비되지 않은 노드로의 급격한 전환
기존 로직은 키의 조회수가 설정한 임계치에 도달하는 순간, 해당 키를 핫키로 분류하고 즉시 라우팅 경로를 변경했다. 문제는 대체 노드가 선정된 직후에는 해당 노드의 메모리에 데이터가 존재하지 않는다는 점이다.

* **승격 전**: 모든 트래픽이 주 노드로 향함 (대체 노드는 비어 있음).
* **승격 직후**: 핫키 판정 즉시 트래픽의 절반이 대체 노드로 전환됨.
* **결과**: 데이터가 없는 대체 노드에서 대규모 캐시 미스 발생 및 DB 부하 급증 (Thundering Herd 현상).

### 기술적 딜레마: 부하 분산과 가용성의 충돌
트래픽 분산이 시급한 핫키 상황임에도 불구하고, 데이터가 없는 노드로 트래픽을 넘기는 것은 시스템 안정성을 해친다. 즉, **부하를 나누는 것**과 **데이터 가용성을 유지하는 것** 사이의 균형을 맞출 완충 장치가 필요했다.


## 트래픽 전환 유예와 데이터 예열을 위한 Guard Phase 설계

이 문제를 해결하기 위해 핫키 승격 직후, 실제 트래픽 분산을 잠시 미루는 **Guard Phase**를 도입하였다.

### 예열 구간의 개념: 의도적 전환 지연
핫키로 판명되었더라도 즉시 트래픽을 나누지 않는다. 대신 일정 횟수(Window Size)만큼은 여전히 주 노드가 모든 읽기 요청을 처리하도록 강제한다. 이 '유예 기간' 동안 시스템은 대체 노드에 데이터를 적재할 시간을 벌게 된다.



### 결정론적 대체 노드 선정 (Deterministic Selection)
대체 노드를 선정할 때 단순히 무작위 노드를 고르지 않는다. 보조 해시(Auxiliary Hash)를 사용하여 주 노드와 다른 별도의 노드를 결정론적으로 선택함으로써, 여러 클라이언트가 동일한 키에 대해 항상 같은 대체 노드를 바라보도록 설계하여 데이터 일관성을 높였다.

### 윈도우 기반 트래픽 스위칭 구현

~~~python
def get_node(self, key, op="read"):
    # 1. 쓰기 요청은 데이터 일관성을 위해 항상 주 노드로 라우팅
    if op == "write":
        return self._primary_safe(key)

    # 2. 핫키 감지 및 카운터 증가
    cnt = self.reads.get(key, 0) + 1
    self.reads[key] = cnt
    
    # 3. 임계치(T) 미만일 경우 기존대로 주 노드 반환
    if cnt < self.T and key not in self.alt:
        return self._primary_safe(key)

    # 4. 핫키 승격 및 대체 노드 확보 (결정론적 방식)
    self._ensure_alternate(key)

    # [Guard Phase 핵심 로직]
    # 승격 후 첫 번째 구간(W) 동안은 트래픽을 분산하지 않고 주 노드 유지
    # 목적: 대체 노드에 데이터가 캐싱될 시간(Warm-up) 확보
    delta = max(0, cnt - self.T)
    if delta < self.W:
        return self._primary_safe(key)

    # 5. 예열 완료 후: 구간(Epoch)별 트래픽 교차 분산 시작
    epoch = (delta - self.W) // self.W
    return self.alt[key] if (epoch % 2 == 0) else self._primary_safe(key)
~~~

### Dual Write를 통한 적극적 데이터 적재
예열 구간 동안 단순히 기다리는 것이 아니다. 이 기간에 발생하는 쓰기 연산 시 주 노드뿐만 아니라 결정된 대체 노드에도 데이터를 함께 기록(Dual Write)하여 트래픽 전환 시점의 적중률을 극대화한다.


## 전환 비용 제로화를 위한 물리적 시간의 고려

1.  **지연 시간 스파이크 억제**: 도입 전에는 승격 시점에 레이턴시가 튀었으나, 도입 후에는 대체 노드가 충분히 예열된 상태에서 트래픽을 넘겨받게 되어 전환 비용이 사실상 사라졌다.
2.  **시스템 응답 안정성 우선**: 예열 기간 동안 주 노드가 부하를 조금 더 견뎌야 하지만, 이는 **즉각적인 분산**보다 **전체 시스템의 응답 안정성**을 선택한 결과이다.

분산 시스템에서 상태 전환은 가장 취약한 지점이다. D-HASH 개발 과정에서 경험한 콜드 스타트 문제는 **"알고리즘의 논리적 완결성만큼이나 데이터가 실제로 안착할 시간을 고려하는 것이 중요하다"**는 사실을 시사한다. 예열 구간은 이러한 물리적 제약을 소프트웨어적으로 보정하는 필수적인 장치이다.


## 실험 데이터로 증명된 부하 분산 효과

실제 벤치마크 실험 결과, Guard Phase를 포함한 D-HASH 전략은 시스템 안정성 면에서 유의미한 수치를 보여주었다.

* **부하 불균형 해소**: 쏠림 현상이 극심한 Zipf 분포($\alpha=1.5$) 환경에서 기존 Consistent Hashing의 부하 표준편차는 **49,944**에 달했으나, D-HASH 적용 시 **33,054**로 약 **33.8% 개선**되었다.
* **전환 비용 최소화**: 도입 전 관측되었던 승격 시점의 레이턴시 스파이크가 사라졌으며, 대체 노드가 충분히 예열된 상태에서 트래픽을 넘겨받아 전환 비용이 사실상 사라졌다.
* **처리량 유지**: 약 7% 수준의 미미한 처리량(Throughput) 저하는 발생했으나, 서버 간 부하 불균형을 획기적으로 줄여 전체 시스템의 가용성을 높였다.

분산 시스템에서 상태 전환은 가장 취약한 지점이다. D-HASH 개발 과정에서 경험한 콜드 스타트 문제는 **"알고리즘의 논리적 완결성만큼이나 데이터가 실제로 안착할 시간을 고려하는 것이 중요하다"**는 사실을 시사한다. 예열 구간은 이러한 물리적 제약을 소프트웨어적으로 보정하는 필수적인 장치였다.
